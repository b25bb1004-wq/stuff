# T15 kairos (crates/kairos): work-stealing thread pool on std threads, driven by the core
Worker: haiku (medium), budget 150k tokens. First read `briefs/_RULES.md`, then `briefs/T05.md`
and `crates/kairos/src/*` (the scheduler core).

**May touch:** `crates/kairos/**` only. Keep every T05 test passing. The core stays `no_std`.
Add a cargo feature `std` (in `default`) that turns on `pub mod pool` (`extern crate std` under
that feature). Zero external crates; `#![forbid(unsafe_code)]` stays.

## Why
Mercury's server (T37) and later tools need a thread pool. The kernel (T26) will use the same
scheduler core without `std`. The pool shows the core works with real threads.

## Public API (exact, in `kairos::pool`)
```rust
pub struct Pool;
impl Pool {
    pub fn new(threads: usize) -> Pool;                         // threads >= 1
    pub fn spawn<F: FnOnce() + Send + 'static>(&self, f: F);    // never blocks for long
    pub fn wait_idle(&self);           // returns when every spawned job (and jobs they spawn) has run
    pub fn shutdown(self);             // waits for queued jobs, then joins every thread
    pub fn stats(&self) -> PoolStats;
}
impl Drop for Pool { /* same as shutdown */ }
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub struct PoolStats { pub spawned: u64, pub completed: u64, pub stolen: u64 }
pub fn current() -> Option<Handle>;     // inside a job: a handle to spawn more jobs on its pool
#[derive(Clone)] pub struct Handle;  impl Handle { pub fn spawn<F: FnOnce() + Send + 'static>(&self, f: F); }
```
## Behaviour
- One local deque per worker (std `Mutex<VecDeque>` is fine), a shared injector queue for
  `spawn` from outside. A worker pops its own deque from the back, then the injector, then steals
  from the front of a random other worker's deque (count it in `stolen`).
- Idle workers sleep on a `Condvar`, never spin for more than a few tries.
- Use `Scheduler` from the core to decide which worker runs next when several are idle and jobs
  arrive (spawn one core task per worker; `pick` decides). Keep it simple; correctness first.
- A job that panics must not kill the worker or lose other jobs: catch it with
  `std::panic::catch_unwind`, count it as completed, keep going.
- `shutdown` and `Drop` never deadlock, even when called while jobs are still spawning jobs.

## Tests required
- 1 000 000 tiny jobs across 8 threads: every job runs exactly once (atomic counter and a
  per-job flag array), `completed == spawned`.
- Recursive spawning (a tree of 100 000 jobs, each spawning two children through `current()`),
  `wait_idle` returns only after all ran.
- Stealing happens: one producer pushes 10 000 slow-ish jobs onto one worker's deque, `stolen > 0`.
- A panicking job: other jobs still run, the pool still shuts down.
- Shutdown while busy: 50 runs of spawn-then-immediate-shutdown, all queued jobs run, no hang
  (each test wrapped in a 60 s watchdog thread that aborts with a message).

## Extra check the leader will run
Its own 8-thread soak with a fresh seed, nested spawns, panics, and repeated create/shutdown.
