## Why
The Rust kernel (T25) and the hypervisor (T31) run tens of millions of instructions in tests;
fetch + decode on every step is the hot path.

## What to build
- A cache of decoded instructions used by `Machine::step`, keyed so that it can never return an
  instruction that differs from what an uncached fetch + decode would produce at that moment.
  Design is yours (per-page decoded arrays, basic blocks, ...). Translation (Sv39) may be redone
  per fetch or cached too; if you cache translations, flush them on `satp` writes, `sfence.vma`,
  privilege changes and stores to page-table memory.
- `machine::Config` gains `pub decode_cache: bool` (default `true`). With `false`, `Machine::step`
  behaves exactly as today. Fix existing struct literals of `Config` in tests.
- Invalidation must cover every way RAM changes: CPU stores of every width (SB/SH/SW/SD, the
  compressed stores, AMOs, successful SC), block-device DMA (`Ram::load` from `block.rs`),
  `Machine::load`, and partial overwrites (a store touching only half of a 4-byte instruction, a
  4-byte instruction straddling a page or block boundary). FENCE.I may stay a no-op.
- Observable behaviour is identical with the cache on and off: the same `Step` results, the same
  `Cpu` state after every step (traps, tval, `instret`, CSRs, reservation), the same RAM, UART,
  framebuffer and disk. Keep the cache out of `Cpu`'s derived `PartialEq` (put it in `Machine`, or
  implement `PartialEq` by hand over the architectural fields only).
- `crates/quartz/examples/bench.rs`: `cargo run --release -p quartz --example bench` prints one line
  `bench: cache-on <X> MIPS, cache-off <Y> MIPS, speed-up <X/Y>x` measured on (a) running
  `tests/fixtures/ac/smoke.bin` to its finisher write, repeated until at least 20 M instructions,
  and (b) a tight 10 M-instruction loop of your choice; report both, the line above is their total.
- `docs/BENCH.md`: a `## quartz` section with the numbers, the machine they were measured on
  (CPU model only) and the command.

## Targets
- Release build speed-up of at least **1.3x** on the bench total (`cache-on / cache-off`), and the
  cache-off path no slower than before your change (within 5%; measure before you start).
- The leader runs everything below in debug test builds, so keep the cache cheap to create
  (no 16 MiB tables allocated up front).

## Tests required
Lockstep tests (two `Machine`s, cache on and off, `Cpu` compared after every step) on every
fixture program, self-modifying code for each store kind listed above, DMA overwriting code that
already ran, code straddling a 4 KiB page, a page-table remap of executing code with
`sfence.vma`, and random instruction streams that store into their own code.

## Extra check the leader will run
`crates/quartz/tests/cache_leader.rs`: lockstep on every fixture in `tests/fixtures/machine` and
`tests/fixtures/ac`; self-modifying programs patching a called routine through SW, two SH, four SB,
SD, AMOSWAP.W, LR/SC, block DMA, a compressed routine, and a routine straddling 0x1000; an S-mode
program whose code page is remapped (PTE change + `sfence.vma`) and rewritten through its physical
alias; 300 random programs of 1024 random valid instructions with registers pointing into their own
code, 3000 lockstep steps each; RAM, UART, framebuffer and disk compared at the end; then the
release bench (speed-up >= 1.3x).
