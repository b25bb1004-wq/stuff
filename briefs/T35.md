## Public API (crate root, exact)
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub struct Lossy { pub drop_per_mille: u32, pub dup_per_mille: u32, pub delay_per_mille: u32, pub seed: u64 }
#[derive(Debug)]
pub enum UdpError { Io(std::io::ErrorKind), Conn(Error), TimedOut, BadHash, BadFrame }
pub fn echo_server(socket: UdpSocket, secret: [u8; 32], seed: [u8; 32], config: Config, lossy: Lossy,
    stop: &AtomicBool) -> Result<(), UdpError>;
pub fn echo(socket: UdpSocket, server: SocketAddr, server_key: [u8; 32], seed: [u8; 32], config: Config,
    lossy: Lossy, data: &[u8], timeout: Duration) -> Result<Vec<u8>, UdpError>;
pub fn recv_file(socket: UdpSocket, secret: [u8; 32], seed: [u8; 32], config: Config, lossy: Lossy,
    out: &mut dyn Write, timeout: Duration) -> Result<(u64, [u8; 32]), UdpError>;
pub fn send_file(socket: UdpSocket, server: SocketAddr, server_key: [u8; 32], seed: [u8; 32], config: Config,
    lossy: Lossy, input: &mut dyn Read, len: u64, timeout: Duration) -> Result<[u8; 32], UdpError>;
```

## Behaviour
- **Driver loop** (shared by all four): flush every `poll_transmit` datagram to the peer address,
  then wait for one datagram with `set_read_timeout` equal to the time until the connection's (or
  server's) `timeout()` (at least 1 ms, at most 50 ms), feed it with `handle`, and call
  `on_timeout` when the timer has passed. Time is microseconds from one `Instant` taken at start.
  `WouldBlock`/`TimedOut` reads are not errors. Other socket errors are `Io(kind)`.
- **Lossy** applies to datagrams this side SENDS, decided by a seeded `assay`-free RNG of your own
  (xorshift64 from `seed`; seed 0 means no loss at all): drop with probability
  `drop_per_mille/1000`; else duplicate with `dup_per_mille`; else hold the datagram back and send
  it after the next 1 to 3 datagrams with `delay_per_mille` (reordering). Held datagrams are
  flushed before the function returns.
- **Echo server:** serves any number of clients at once (map cid to `SocketAddr` from
  `Server::handle`). Every stream a client opens is echoed back on the same stream, byte for byte,
  and finished once the client has finished it. Runs until `stop` is true (checked every loop).
- **echo:** connects, opens one stream, writes `data` (respecting flow control: write what
  `write` accepts, drive, repeat), finishes it, reads until the server finishes, closes the
  connection with code 0, returns the bytes. Not connected or not done within `timeout`: `TimedOut`.
- **File transfer:** the client opens one stream and sends `len` as 8 bytes LE, then exactly `len`
  bytes from `input`, then finishes. The server writes the payload to `out`, then replies on the
  same stream with the 32-byte SHA-256 of the payload (`sphinx` sha256) and finishes. `send_file`
  computes its own hash while sending; a reply that differs is `BadHash`, a reply not 32 bytes is
  `BadFrame`. `recv_file` handles exactly one client and one file, returns `(len, hash)`; a stream
  that ends before `len` payload bytes is `BadFrame`. Both close cleanly when done.
- A wrong `server_key` must make `echo`/`send_file` fail (handshake never completes: `TimedOut`,
  or `Conn(..)`), never hang past `timeout`.
- **Tool** `src/bin/xenon.rs` (thin wrapper, no logic of its own):
  `xenon keygen` prints a secret and public key in hex; `xenon echo-server <addr> <secret-hex>`;
  `xenon echo <addr> <pubkey-hex> <text>`; `xenon recv <addr> <secret-hex> <out-file>`;
  `xenon send <addr> <pubkey-hex> <file>`. Seeds come from hashing the system time and process
  id with sha256. Errors print one line and exit 1. `main` may use `?` but must not `unwrap`.
