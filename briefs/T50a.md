## Public API (exact)
```rust
// seam::node
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Msg { Block(Block), Tip { hash: Hash, height: u64 }, GetBlock(Hash), Tx(Tx) }
impl Msg { pub fn encode(&self) -> Vec<u8>; pub fn decode(b: &[u8]) -> Result<Msg, DecodeError>; }
pub struct Node { /* private */ }
impl Node {
    pub fn new(genesis: &[(Address, u64)], validators: &[Address]) -> Node;
    pub fn chain(&self) -> &Chain;            // the chosen chain
    pub fn tip(&self) -> Hash;                // hash of the chosen chain's tip header
    pub fn known(&self, h: &Hash) -> bool;    // block stored (valid or orphan)
    pub fn pending(&self) -> &[Tx];           // mempool, in arrival order, no duplicates
    pub fn handle(&mut self, msg: Msg) -> Vec<Msg>;     // replies and gossip to send to all peers
    pub fn propose(&mut self, seed: &[u8; 32], time: u64) -> Option<Block>; // on its own tip
    pub fn reorgs(&self) -> u64;              // times the tip moved to a non-descendant
}
```

## Rules (exact; the leader models them)
- Known blocks form a tree from genesis. A block whose parent is unknown is kept as an orphan
  (at most 256; oldest dropped first) and `handle` returns `GetBlock(parent)`. When the parent
  arrives, orphans are connected (repeatedly).
- A block is valid when `Chain::append` accepts it on top of its parent's chain state (replay from
  genesis or keep per-branch states; either is fine). Invalid blocks are dropped with every
  descendant and never re-requested.
- Fork choice: the valid branch with the greatest height; ties go to the smaller tip hash
  (byte order). A switch to a non-descendant counts one reorg.
- `handle(Block)` of a new valid block that changes the tip returns `[Block(b), Tip{..}]` for
  gossip; a known block returns nothing. `handle(Tip)` for an unknown hash returns
  `GetBlock(hash)`. `handle(GetBlock(h))` returns `Block` if known, else nothing.
- `handle(Tx)` adds a tx not yet in the mempool and not in the chosen chain, and gossips it once.
  After a tip change the mempool drops txs now in the chosen chain and re-adds txs from
  abandoned blocks (in block order). `propose` uses the mempool in order, at most `MAX_TXS`,
  skipping txs the chain rejects, appends the block to the node and returns it.
